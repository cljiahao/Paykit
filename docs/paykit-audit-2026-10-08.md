# Paykit audit, 2026-10-08

Status: expanded source remediation prepared; final coverage rerun and local database validation remain outstanding. Read the latest source-review appendix below for superseding findings. No deployment, remote database changes, commits, or pushes.

## Fixed and covered by regression tests

- Checkout idempotency now rejects reuse of a kit/order reference for a different vendor or amount with HTTP 409. Previously the duplicate lookup could return another checkout's persisted payload.
- Checkout retries reject a persisted payload that differs from the current rendered payment configuration. This prevents an old PayNow payload being returned as a link or image after configuration changes. Limitation: configuration changes require a fresh order reference; exact historical replay needs a persisted checkout-view snapshot, including type and label.
- Claim, confirm, and unclaim return HTTP 503 when their conditional update fails and a reread shows no state change. Concurrent successful transitions still return their actual latest state. Previously a failed database mutation could be reported as a successful response with unchanged state.
- Vitest explicitly sets envDir:false so local dotenv files are not loaded by Vite during verification.

## Review findings requiring follow-up

- DRY/SRP: claim/confirm/unclaim share substantial request/auth/rate-limit/read/conditional-write/reread behavior. Their transition differences are small; a shared typed transition handler is a reasonable future refactor once behavior tests are retained.
- Historical pointer payloads cannot distinguish links from QR images. Migration0018 and checkout-kind resolution prepare an immutable snapshot for new checkouts; ambiguous older URLs deliberately remain unavailable for replay/display. See the appendix for compatibility behavior.

## Boundaries inspected

Kit bearer authentication hashes secrets and uses constant-time comparisons. Cross-kit API trusts authenticated kits by design; vendor/kit ownership scoping was not widened or silently redefined. Dashboard booking access uses the vendor session before service-role linking. Rate limiting is explicitly best-effort and fails open by existing design. Booking QR SVG is generated by qrSvg from payload rather than accepting raw HTML from callers.

No files were deleted based solely on an apparent lack of references. Framework entry points and externally callable endpoints need explicit reachability evidence before removal.

## Final remediation evidence

- Migration `0016_recover_booking_deposit.sql` adds a service-only linking RPC that verifies booking ownership, transaction identity/amount, cancellation and existing links. It locks transactions in stable order before the booking, and reconciles already-confirmed deposit/balance status. Normal booking creation uses the same RPC.
- Best-effort kit authentication telemetry now tolerates rejected promises without changing authentication outcomes.
- Platform totals and vendor summaries now read all pages; the parent verified 43 auth/admin tests including a 1,001-transaction dataset. Security-event summaries were subsequently paginated as part of the full-source review.
- Migration0017 applies the same constrained linking and lock order to balance checkouts. The confirmation trigger locks bookings in deterministic order before separately reading both payment statuses, addressing simultaneous deposit/balance confirmations under READ COMMITTED. Cancellation guards remain in place. Runtime concurrency verification is still outstanding.
- Parent verification: 73 booking tests passed after recovery changes. The earlier full coverage figures above are a baseline, not a claim about the expanded final change; the final full gate is being rerun.
